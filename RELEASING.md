# Releasing

Maelys HTTP publishes through the maelys-release socle. `.github/workflows/release.yml`
is generated by `maelys-release adopt` and must never be edited by hand: what
this repository decides about its release lives in `maelys-release.conf`, and
what it runs lives in `scripts/`.

## What this repository declares

`maelys-release.conf` holds the reasoning as well as the values.

- **Three targets verify, two package** (`[package] linux-x86_64
  macos-arm64`), each under names of its own. At the tag, linux-x86_64,
  linux-arm64 and macos-arm64 each replay the source, install and TLS gates.
  linux-x86_64 builds the source archive: `git archive` writes the same tar
  everywhere but gzip does not, and three runners compressing one tree into
  three different archives is a clash the socle refuses. macos-arm64 builds
  the binary archive described below.
- **`*.tar` and `*.spdx.json`** beyond the socle's `*.tar.gz`. What the
  manifest does not name is attested and never published.
- **`*.spdx.json` as the SBOM**, one document per packaging target, attested
  against the file the document itself names, never against a file paired
  with it by convention.
- **A reviewer gate** on the `release` environment. With one maintainer the
  approver and the tagger are the same person, so it is a pause rather than a
  control — and a pause is what was missing the day a tag was pushed before its
  verdict had been read.
- **`[commit] signed-on-default-branch`**: the commit the tag names carries its
  own GitHub-verified signature and is an ancestor of the default branch.
- **`[dependencies] apart`**: the pinned checkouts live under
  `$MAELYS_DEPENDENCIES_DIR` and never beside this repository, which is where
  the working copy of somebody who also develops Maelys System would sit.
- **`[cut] after-version`**: the version is materialised twice, here and in
  `include/maelys/http.h`, and `cut` copies one into the other inside the bump
  commit.

## Repository controls

- Protect `main` and require review for workflow and release-key changes.
- Restrict creation and deletion of `v*` tags to release maintainers.
- The keys that may sign a release are the socle's list,
  `share/allowed-signers` of maelys-release, read at the socle commit this
  repository pins. A key is added or rotated there, and reaches this
  repository at its next adoption.
- Require signed commits on `main`.
- Require a reviewer on the `release` environment, which is where the
  publication waits.

These server-side rules are part of the trust boundary: a workflow cannot
protect itself from an actor allowed to replace both the release ref and its
workflow definition.

## Who may publish

GitHub reports a tag as verified when *any* key *any* account registered signed
it. That says a signature is genuine; it does not say the signer may release
this product. The socle answers the second question, in its `verify` job,
before any build job starts:

1. the tag is annotated, verified by GitHub, equal to `VERSION`, and names the
   checked-out commit;
2. its signature is SSH and verifies against `share/allowed-signers` of
   maelys-release, read at the socle commit `release.yml` pins — so the list
   travels with the version this repository adopted, and a retired key is
   judged at the moment GitHub saw the tag, not at a date its signer wrote;
3. the commit carries its own verified signature and is an ancestor of the
   default branch, because `maelys-release.conf` declares
   `[commit] signed-on-default-branch`.

This repository carried the first two points itself from 0.1.13 to 0.1.15, in
`scripts/verify-tag-signature.sh` and `.github/release-allowed-signers`, while
the socle had no such list. It has had one since v0.62.0, the 0.1.15 release
passed through both, and two lists naming one key are one list too many: the
second is where a rotation gets forgotten.

`maelys-release preflight .` says, before there is a tag, whether the key this
checkout would sign with is named in that list. A tag the release refuses is a
tag that is burned, since a published tag is never moved, and `cut` asks the
same question before it signs.

## Release sequence

1. `maelys-release cut . X.Y.Z --apply` writes `VERSION`, commits it signed on
   `release/vX.Y.Z`, opens the pull request and waits for its checks. It never
   merges its own pull request.
2. Merge it. `ci.yml` runs on the merge commit: the shared check on
   linux-x86_64, linux-arm64 and macos-arm64, the second compiler on both Linux
   architectures, and the physical TLS lifecycle against pinned Mbed TLS on
   Linux and Homebrew's on macOS.
3. `maelys-release cut . X.Y.Z --tag --apply` checks the signing key against
   the socle's list, then signs the tag on that merge commit.
4. The socle's `verify` job runs the three checks of the previous section.
5. The `build` job runs once per target. Each materialises every pin under
   `$RUNNER_TEMP/dependencies` with `scripts/checkout-dependencies.sh`, exports
   the root, and runs `scripts/verify-release.sh TARGET` — `make check
   install-check check-system-pin` and `make tls-integration
   REQUIRE_MBEDTLS=1`, against the Mbed TLS commit `dependencies/mbedtls.pin`
   names on Linux, built by `scripts/build-pinned-mbedtls.sh`, and against
   Homebrew's on macOS. linux-x86_64 and macos-arm64 then run
   `scripts/package-release.sh TARGET`. On linux-x86_64 it writes the source
   archives, their digests, the reproducibility check, the SBOM and the build
   of the extracted archive. On macos-arm64 it hands over to
   `scripts/package-macos-archive.sh`, which writes the binary archive, its
   digest and its SBOM. No build job holds a write token.
6. The `publish` job waits for the reviewer, downloads what `build` produced,
   re-verifies every digest, writes `SHA256SUMS` and creates the release. It is
   the only job that may write.
7. `tap-libmaelys-http` renders `packaging/homebrew/libmaelys-http.rb.in` with
   `scripts/render-homebrew-formula.sh`, builds bottles on macos-15 and
   macos-26, attaches them to the release and pushes the formula to
   `maelys-dev/homebrew-tap`.

The formula is rendered from the **published** archive: the script downloads
it, hashes those exact bytes, and reads the template, `VERSION` and the Maelys
System pin from inside that same archive. The tap renders on macOS while the
release built on Linux, and gzip is not byte-identical between the two, so a
formula hashing a locally rebuilt archive would name a digest no downloader
ever computes. It is also why the tap job needs the release job.

## The macOS binary archive

`maelys-http-VERSION-macos-arm64.tar.gz` is laid out like maelys-system's
archive: under `usr/local`, the three static archives `libmaelys_http.a`,
`libmaelys_http_client.a` and `libmaelys_http_tls_mbedtls.a`, the public
headers, the three pkg-config files and `share/maelys-http/build-info`. It
carries no shared library, no Mbed TLS and no `libmaelys_sys.a`: maelys-system
publishes its own archive, and `maelys-http-client.pc` requires the version
`dependencies/maelys-system.pin` names.

Mbed TLS is the consumer's to link, and that is why the provider is not
compiled against `dependencies/mbedtls-4.pin` built from source. It embeds Mbed
TLS structures whose size depends on the configuration as well as the
version: Homebrew's 4.2.0 turns on `MBEDTLS_THREADING_C`,
`MBEDTLS_THREADING_PTHREAD` and `MBEDTLS_SSL_DTLS_SRTP`, and its
`mbedtls_ssl_context` is 848 bytes where the upstream default is 584. A
provider compiled against the default and linked with Homebrew's would let
Mbed TLS write past every session it allocates. The archive is therefore
compiled against Homebrew's Mbed TLS, which a macOS consumer links and the
bottles use, and the script refuses to package unless that is the version
`dependencies/mbedtls-4.pin` names. `maelys-http-tls-mbedtls.pc` accepts that
minor line only (`>= 4.2.0, < 4.3`), since Mbed TLS keeps structure layouts
across patch releases only, and `build-info` records the version, the three
options and the structure sizes.

Before it writes the SBOM, the script plays a consumer: it installs
maelys-system from its pinned checkout, extracts the archive beside it, links
`tests/tls_integration_client.c` statically from the libraries the pkg-config
files name, requires `otool -L` to list only `libSystem`, and runs
`scripts/test-tls-integration.sh` with that client.

The provenance of a published file is verified against the socle's workflow
and the tag:

```sh
gh attestation verify maelys-http-X.Y.Z-macos-arm64.tar.gz \
  --repo maelys-dev/maelys-http \
  --signer-workflow maelys-dev/maelys-release/.github/workflows/release.yml \
  --source-ref refs/tags/vX.Y.Z
```

## Replaying a failed publication

A published tag is never moved, recreated or force-pushed. Run the `release`
workflow with `workflow_dispatch` and the existing tag: the socle redrafts the
release, empties its assets and fills it again, so a replay never leaves an
asset of a former attempt behind. `scripts/render-homebrew-formula.sh` reads
the tag's own published bytes, so it behaves identically whether the run came
from a tag push or a dispatch.

Never bypass a failed verification, pin, Mbed TLS security-floor or checksum
check. A distribution build may define
`MAELYS_HTTP_MBEDTLS_ALLOW_BACKPORTED_SECURITY_FIXES` only after verifying that
its maintained package carries every applicable upstream security fix.

## Building it by hand

The pinned checkouts live apart from this repository and no path is assumed,
so one line puts them somewhere and says where:

```sh
eval "$(sh scripts/checkout-dependencies.sh "$PWD/../maelys-http-deps")"
```

`maelys-release dependencies . --apply` prints the same assignment and, unlike
the script, refreshes a root that already exists instead of refusing it. From
there `make check`, `bash scripts/verify-release.sh <target>` and `bash
scripts/package-release.sh <target>` are exactly what the release runs; the
macos-arm64 archive is packaged on a Mac with Homebrew's Mbed TLS.

Before a tag that changes the release or its packaging, replay the Linux build
job in a bare container, where nothing the runner image happens to carry can
hide an undeclared tool:

```sh
maelys-release rehearse . linux-arm64 --check --check-command "bash scripts/verify-release.sh linux-arm64"
maelys-release rehearse . linux-x86_64
```
